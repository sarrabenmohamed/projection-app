A JSON object with a points array. Everything except points[].id, points[].lang, and points[].vector is optional:

{
  "model": "any string (informational)",
  "layer": "any string (informational)",
  "dim": 768,
  "lang_codes": ["en", "de"],
  "points": [
    {
      "id": "unique-string-or-number",
      "lang": "en",
      "text": "shown in tooltip + data table",
      "vector": [0.1, -0.4, ...],
      "pairId": 0,
      "tokenVectors": [
        {"token": "shown", "vector": [0.2, -0.1, ...]}
      ]
    }
  ]
}

tokenVectors is optional — if present, selecting this point in the data table reveals a "Show tokens" action, projecting its tokens into the same UMAP space as the main plot. They only make sense if they come from the same model/layer/pooling as vector — token vectors from a different embedding space will plot in meaningless positions.

vector can be any length, but every point must have the same length.

pairId is optional — points sharing one are treated as translations of each other (isolated together on click). Omit it entirely if your data isn't parallel; each point will isolate alone instead.

dim / lang_codes are inferred automatically if omitted.

Floats only need ~6 decimal places — embeddings are almost always float32 under the hood (~7 significant digits), so full float64 precision just bloats the file for no benefit.

Size guidance: both file size and UMAP fit time scale with points × dim, so keep datasets in the thousands of points rather than hundreds of thousands.

What this plot can't tell you — both UMAP and t-SNE only try to preserve local neighborhoods, so:

  • Distance between separate clusters isn't meaningful. Two clusters drawn far apart aren't necessarily "more different" than two drawn close together — only which points are near each other within a cluster is (approximately) preserved.
  • Cluster size/density on screen ≠ density in the real embedding. t-SNE especially tends to draw similarly-sized, evenly-spaced blobs regardless of how tight or spread out the original high-dimensional cluster actually was.
  • The layout is hyperparameter-dependent. n_neighbors/perplexity control the local-vs-global tradeoff directly — a different value can visibly reshape, split, or merge clusters. What you're looking at is a view of the structure under the current settings, not the structure.
  • The fixed random seed makes this reproducible, not "correct." The same settings always give the same layout, but a different seed (not exposed here) could give a different one just as valid.
  • "Show tokens" projects into an already-fit space. New points (a sentence's tokens) are approximately fit into the existing UMAP space via .transform() rather than being part of the original fit, so they're inherently less reliable than the sentence points themselves.
