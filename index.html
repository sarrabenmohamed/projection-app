JSONL (.jsonl): one point object per line (id, lang, vector, ...). Optional leading lines without a vector carry metadata such as model or lang_families.

CSV / TSV (.csv, .tsv): a header row with id, lang and optionally text, pairId, family. The vector is either a single vector column ([0.1, -0.4] or space-separated numbers) or one numeric column per dimension (v0, v1, ...; every column that isn't named above). Token vectors need JSON.

JSON: an object with a points array. Everything except points[].id, points[].lang, and points[].vector is optional:

{
  "model": "any string (informational)",
  "layer": "any string (informational)",
  "dim": 768,
  "lang_codes": ["en", "de"],
  "lang_families": {"en": "Germanic", "de": "Germanic"},
  "points": [
    {
      "id": "unique-string-or-number",
      "lang": "en",
      "text": "shown in tooltip + data table",
      "vector": [0.1, -0.4, ...],
      "pairId": 0,
      "tokenVectors": [
        {"token": "shown", "vector": [0.2, -0.1, ...]}
      ]
    }
  ]
}

tokenVectors is optional — if present, selecting this point in the data table reveals a "Show tokens" action, projecting its tokens into the same UMAP space as the main plot. They only make sense if they come from the same model/layer/pooling as vector — token vectors from a different embedding space will plot in meaningless positions.

vector can be any length, but every point must have the same length.

pairId is optional — points sharing one are treated as translations of each other (isolated together on click). Omit it entirely if your data isn't parallel; each point will isolate alone instead.

dim / lang_codes are inferred automatically if omitted.

lang_families (language code → family name) and a per-point family are optional and only affect "Color by language family". Without them, codes such as deu_Latn, deu, de or German are looked up in Glottolog; anything unknown falls into "Other". A point's family beats lang_families, which beats Glottolog.

Floats only need ~6 decimal places — embeddings are almost always float32 under the hood (~7 significant digits), so full float64 precision just bloats the file for no benefit.

Size guidance: both file size and UMAP fit time scale with points × dim, so keep datasets in the thousands of points rather than hundreds of thousands.

UMAP and t-SNE only preserve local neighborhoods:

  • Distances between clusters, and cluster sizes, aren't meaningful.
  • The layout depends on the parameters — it is a view of the structure, not the structure.
  • Token points are fitted into the existing UMAP space, so they are less reliable than sentence points.
